# Implementation Plan: مدیریت درخواست تغییر

**Branch**: `001-change-request-management` | **Date**: 2026-11-16 | **Spec**: [spec.md](spec.md)

**وضعیت تصمیم‌ها**: انتخاب‌های فنی اصلی در پیام مالک محصول تأیید شده‌اند. جزئیات اجرایی این نسخه در Research تثبیت شده‌اند؛ gate سازگاری واقعی driver روی Windows/Node در T001 پیش‌نیاز Implement است.

## خلاصه

نسخهٔ اول شامل HTTP API و رابط سادهٔ React + TypeScript + Vite است. انتخاب‌های اصلی Node.js + TypeScript + Express، SQLite محلی، ورود گذرواژه‌ای، scrypt، نشست پایدار و CLI تأمین نقش تأیید شده‌اند. ترتیب تحویل: ابتدا API و آزمون‌های Backend، سپس UI. منطق گردش و مجوز در Application/Domain می‌ماند و لایهٔ HTTP فقط ورودی، نتیجه و خطای قراردادی را نگاشت می‌کند. جزئیات scrypt/session/CSRF/SQLite در Research تثبیت شده‌اند؛ gate سازگاری native driver روی Windows پیش‌نیاز اجراست.

## زمینهٔ فنی

**زبان/نسخه**: Node.js 26 LTS و TypeScript تأیید شده‌اند. Node `26.13.1` baseline بررسی‌شده است؛ T001 نسخهٔ patch جاری و نسخه‌های دقیق همهٔ packageها را pin و با lockfile ثبت می‌کند.

**وابستگی‌های اصلی**: Express 5 و React + TypeScript + Vite تأیید شده‌اند. SQLite driver پیشنهادی `better-sqlite3@13.1.1` است؛ پیش از هر کار وابسته باید T001 نصب واقعی روی Windows/Node هدف، بارگذاری native binary، تراکنش، rollback و contention را بررسی کند. این مرحله هیچ package نصب نمی‌کند.

**مدیریت packageها**: پیشنهاد یک npm workspace در ریشه با یک lockfile مشترک برای API و `web/` است؛ این انتخاب نصب تکراری و drift نسخهٔ Node را کم می‌کند و قبل از pin نهایی در T001 ثبت می‌شود.

**ذخیره‌سازی**: SQLite فایل محلی تأیید شده است. Account، Session، RoleGrant و ChangeRequest در همان DB قرار می‌گیرند؛ بررسی نشست/نقش/مالکیت/وضعیت/نسخه و اعمال تغییر در مرز تراکنشی مشترک انجام می‌شود. commit عملیات/لغو نقش نقطهٔ خطی‌سازی است.

**آزمون**: Node `node:test` برای منطق و HTTP/SQLite یکپارچه؛ Vitest + React Testing Library برای component/interaction؛ Playwright برای E2E. آزمون Backend و snapshot دادهٔ ذخیره‌شده الزامی و مستقل از UI است.

**سکوی هدف**: اجرای محلی روی Windows با PowerShell؛ برای پایگاه داده از مسیر محلی فایل استفاده شود. جزئیات مسیر و فرمان‌ها در `quickstart.md` پیشنهاد شده‌اند.

**نوع پروژه**: یک برنامهٔ وب محلی با Backend/API و UI؛ در اجرا UI از API هم‌مبدأ استفاده کند.

**اهداف کارایی**: عدد کارایی محصولی در Spec تعیین نشده است. هیچ SLA یا نرخ درخواست جدیدی فرض نمی‌شود.

**محدودیت‌ها**: ورود با حساب فردی محلی، scrypt و Session پایدار SQLite؛ RoleGrant جاری در همان SQLite؛ CLI محدود برای provisioning؛ لغو مؤثر در commit؛ شمارش با grapheme cluster. هیچ نقش قدیمی از token مبنای مجوز نیست.

**اندازه/دامنه**: یک گردش درخواست تغییر، دو نقش، چهار وضعیت و HTTP API؛ بدون ثبت‌نام/مدیریت کاربر در محصول، حذف، تاریخچهٔ کامل توضیح‌ها یا قابلیت‌های خارج از Spec.

### پیشنهاد احراز هویت و provisioning

حساب فردی با CLI محلی ساخته می‌شود. پارامتر تثبیت‌شدهٔ hash: Node `crypto.scrypt` async با `N=2^17`, `r=8`, `p=1`, `keylen=64`, `maxmem=256 MiB`; salt تصادفیِ مولد امن رمزنگاری و یکتا، 16 بایت. پارامترها همراه رکورد ذخیره می‌شوند تا مهاجرت/rehash ممکن باشد. نشست شناسهٔ تصادفی 32 بایتی دارد؛ SQLite فقط SHA-256 شناسه را ذخیره می‌کند. نشست با idle timeout 30 دقیقه و سقف مطلق 12 ساعت منقضی می‌شود؛ زمان آخرین فعالیت در هر درخواست احرازشده به‌روزرسانی می‌شود؛ نشست منقضی هنگام ورود پاک و CLI فرمان `sessions prune` برای پاک‌سازی دستی دارد. Logout رکورد را حذف می‌کند. این چرخه روی همان DB و بدون MemoryStore اجرا می‌شود.

CLI افزودن/لغو RoleGrant را فقط روی همان فایل SQLite و با همان ترتیب تراکنش/قفل عملیات حساس انجام می‌دهد؛ commit تغییر RoleGrant نقطهٔ مؤثر لغو است. دسترسی به فایل DB و اجرای CLI باید به حساب OS/اپراتور مشخص با ACL ویندوز محدود شود؛ CLI در مسیر عادی HTTP/UI عرضه نمی‌شود. همین ترتیب تراکنشی commit تضمین FR-019 را برقرار می‌کند.

CSRF: توکن تصادفی 32 بایتی برای نشست، نگهداری server-side و ارسال در header `X-CSRF-Token`؛ همهٔ روش‌های تغییردهنده علاوه بر احراز نشست باید توکن و Origin دقیق را بررسی کنند. Login نیز Origin را بررسی می‌کند؛ logout توکن لازم دارد. SameSite=Lax دفاع تکمیلی است؛ CORS فقط same-origin. Cookie `HttpOnly`, `SameSite=Lax`; `Secure` فقط HTTPS. Vite مسیر `/api` را در توسعه به API proxy می‌کند. در deployment واقعی TLS اجباری و proxy مورداعتماد دقیق است. SQLite تک‌میزبان/تک‌نویسنده است؛ چند replica نیازمند بازنگری است.

`better-sqlite3` یک API هم‌زمان دارد؛ تمام Queryها و تراکنش‌ها باید کوتاه بمانند و هیچ KDF/شبکه/کار طولانی داخل تراکنش انجام نشود. DB روی دیسک محلی با `journal_mode=WAL` و `foreign_keys=ON` اجرا می‌شود. تراکنش حساس با `BEGIN IMMEDIATE` آغاز می‌شود. `timeout=5000ms`; پس از SQLITE_BUSY تراکنش rollback می‌شود و بدون retry کور، پاسخ زیرساختی `503` با `Retry-After: 5` برمی‌گردد؛ client باید دادهٔ فعلی را دوباره بخواند و فرمان با version قدیمی replay نشود. T001 نصب واقعی و این رفتارها را روی محیط هدف gate می‌کند. اگر compatibility/build gate شکست بخورد، انتخاب driver جایگزین نیازمند بازبینی Research و توقف کارهای وابسته است.

Backend همهٔ فیلدهای محدودشده را با یک helper `Intl.Segmenter('fa', {granularity:'grapheme'})` می‌شمارد؛ locale در segmentation grapheme نباید مرز متفاوت ایجاد کند. نسخهٔ Node/ICU pin و helper Backend با آزمون Unicode ثابت می‌شود. UI سقف را مستقلاً enforce نمی‌کند و خطای validation برگشتی Backend را نشان می‌دهد تا دو runtime با ICU متفاوت تصمیم متناقض نگیرند. UTF-16 length و byte length معیار نیستند.

### پیشنهاد راهبرد آزمون UI

- آزمون‌های تعاملی مبتنی بر DOM برای فرم ایجاد/ویرایش، نمایش وضعیت و توضیح، نمایش خطاهای validation/permission/conflict و رفتار کنترل‌ها بر اساس نقش.
- آزمون E2E با مرورگر برای ورود/خروج، مشاهدهٔ محدودهٔ Requester/Reviewer، ایجاد و Submit، RequestChanges با توضیح، Approve مستقل و conflict نسخهٔ stale.
- برای UI، APIهای جعلی فقط در آزمون component قابل قبول‌اند؛ آزمون‌های E2E و تمام آزمون‌های امنیت/داده باید Backend واقعی و DB آزمایشی را به‌کار ببرند. آزمون Backend با snapshot دادهٔ ذخیره‌شده اجباری و مستقل باقی می‌ماند.
- آزمون UI نباید کنترل دسترسی را صرفاً با مخفی‌شدن دکمه اثبات کند؛ تلاش مستقیم API نیز باید در مجموعهٔ Backend پوشش یابد.

## ثبت پیچیدگی

نقض قانون‌نامه‌ای وجود ندارد. الگوی Repository صرفاً یک adapter باریک برای تراکنش SQLite است؛ در صورت امکان همان دسترسی محدود و مستقیم در Application کافی است. UI در پوشهٔ `web/` به‌عنوان client سبک نگهداری می‌شود، نه سرویس مستقل و نه محل قواعد کسب‌وکار.
