# قانون‌نامهٔ ChangeFlow (ChangeFlow Constitution)

## اصول بنیادین (Core Principles)

### I. معماری ساده و منطق کسب‌وکار لایه‌بندی‌شده
معماری باید ساده، نگهداشت‌پذیر و مناسب توسعهٔ تدریجی بماند. قواعد کسب‌وکار باید در لایهٔ Domain یا Application قرار بگیرند. Controllerها و Endpointها باید درخواست را دریافت کنند، رفتار برنامه را فراخوانی کنند و نتیجه را به پاسخ HTTP تبدیل کنند؛ نباید قواعد کسب‌وکار را اجرا کنند. لایه‌ها و انتزاع‌ها فقط وقتی افزوده شوند که نیاز اثبات‌شده‌ای هزینهٔ آن‌ها را توجیه کند.

### II. تصمیم‌های امن و انتقال معتبر وضعیت
هر عملیات حساس باید هویت درخواست‌کننده، مجوز فعلی، مالکیت مرتبط و وضعیت فعلی درخواست را بررسی کند. تأیید درخواست توسط ثبت‌کننده ممنوع است، حتی اگر همان فرد نقش Reviewer را نیز داشته باشد. درخواست Approved نباید قابل ویرایش باشد. مجوز باید بر اساس دسترسی‌های معتبر هنگام انجام عملیات سنجیده شود.

### III. قواعد کسب‌وکارِ آزمون‌پذیر
آزمون‌های خودکار باید شش سناریوی حداقلی Assignment.md را پوشش دهند: ایجاد موفق Draft، ارسال معتبر به PendingReview، رد Self-Approval حتی برای کاربر دارای هر دو نقش، تأیید موفق به‌وسیلهٔ Reviewer مستقل و مجاز، رد ویرایش درخواست Approved و جلوگیری از بازنویسی خاموش بر پایهٔ نسخهٔ قدیمی. آزمون‌های حساس باید علاوه بر پاسخ HTTP، وضعیت ذخیره‌شده را نیز بررسی کنند. موفقیت آزمون‌ها به‌تنهایی رعایت معماری یا پذیرش انسانی را ثابت نمی‌کند.

### IV. تصمیم‌های صریح و قابلیت ردیابی
Agent نباید رفتاری را که مالک محصول مشخص یا تأیید نکرده است، بی‌صدا به‌عنوان تصمیم نهایی انتخاب کند. موارد حل‌نشده باید برای Specify/Clarify ثبت شوند؛ فرض‌ها باید صریح باشند و از تصمیم‌های تأییدشده جدا بمانند تا قابل بازبینی باشند. قابلیت ردیابی باید از نیازمندی‌ها، تصمیم‌های طراحی و Taskها تا پیاده‌سازی و آزمون حفظ شود. پوشش نیازمندی‌ها با Taskها به‌تنهایی آمادگی Implement را ثابت نمی‌کند.

### V. تحویل مبتنی بر شواهد و محدودهٔ تدریجی
گزارش‌های Build، Test و Validation باید فقط فرمان‌های واقعاً اجراشده و نتایج مشاهده‌شده را بازتاب دهند. مراحل اجرا‌نشده، خطاها و محدودیت‌ها باید صریح اعلام شوند؛ نتیجهٔ آزمون یا پذیرش انسانی نباید ساخته شود. برای محصول، HTTP API کافی است و Frontend الزامی نیست. قابلیت‌های AI، RAG، MCP و Multi-Agent خارج از محدوده‌اند. ساده‌ترین طراحی‌ای ترجیح دارد که نیازمندی‌های تأییدشده و توسعهٔ تدریجی مورد انتظار را پشتیبانی کند.

## مرزهای محصول و فناوری (Product and Technical Boundaries)

گردش ChangeFlow و قواعدی که در Assignment.md قطعی اعلام شده‌اند، الزام‌آورند. به‌ویژه، رفتار برنامه باید انتقال وضعیت معتبر و مجوزها را اعمال کند و محتوای تأییدشده بدون بازبینی معتبر همان محتوا نباید تغییر کند.

این قانون‌نامه فناوری، روش Persistence یا سازوکار Authentication/Authorization را قطعی نمی‌کند. گزینه‌ها باید در Plan/Research مقایسه و مستند شوند. گزینه‌های کنترل هم‌زمانی نیز باید همان‌جا بررسی شوند؛ این قانون‌نامه جلوگیری از بازنویسی خاموش و وضعیت ناسازگار را لازم می‌داند، اما سازوکار خاصی را تحمیل نمی‌کند.

رفتارهای بازمانده از Assignment.md، مانند حذف Draft، مشاهدهٔ درخواست دیگران، اثر لغو مجوز و درخواست تکراری، باید با تصمیم مالک محصول در Specify/Clarify تعیین شوند یا به‌صورت فرض قابل بازبینی ثبت شوند. فرض نباید به‌جای تأیید تلقی شود.

## گردش توسعه و شواهد (Development and Evidence Workflow)

Analyze بازبینی سازگاری Specification، Plan و Taskها به‌صورت فقط‌خواندنی است. Converge شکاف میان پیاده‌سازی فعلی و قصد مستندشده را بررسی می‌کند و نباید مستقیماً کد را تغییر دهد. کارهای باقی‌مانده‌ای که Converge پیدا می‌کند باید به Taskهای قابل ردیابی تبدیل شوند. Build، Test، Validation و Acceptance ادعاهای جداگانه‌اند؛ فقط مرحله‌هایی را گزارش کنید که واقعاً انجام شده‌اند و بدون ارزیابی انسانی، ادعای پذیرش نکنید.

## حاکمیت (Governance)

این قانون‌نامه بر تصمیم‌های پروژه و کار Agent حاکم است. اگر تصمیم محصولی با آن تعارض داشته باشد، آن تصمیم تا زمانی که قانون‌نامه به‌طور صریح اصلاح و اصلاحیه به تأیید مالک قانون‌نامه نرسیده است، قابل اجرا نیست. ثبت یا تأیید تصمیم محصولی به‌تنهایی تعارض را رفع نمی‌کند. در بازبینی‌های مرتبط، معماری، امنیت، شواهد آزمون، قابلیت ردیابی و رعایت محدوده بررسی شوند؛ موفقیت آزمون جای این بررسی‌ها را نمی‌گیرد.

اصلاحات باید این فایل و فرادادهٔ نسخه و تاریخ آن را به‌روز کنند. از نسخه‌بندی معنایی استفاده کنید: برای تغییر ناسازگار در حاکمیت، MAJOR؛ برای افزودن اصل یا گسترش اساسی الزام‌ها، MINOR؛ و برای شفاف‌سازی یا اصلاح غیرمعنایی، PATCH را افزایش دهید. واقعیت‌های نامعلوم را به‌صورت TODO صریح ثبت کنید و آن‌ها را جعل نکنید.
